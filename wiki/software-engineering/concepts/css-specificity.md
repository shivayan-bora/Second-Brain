# CSS Specificity

## Definition

**Specificity** is the algorithm CSS uses to decide which rule wins when multiple rules target the same element. It's expressed as a tuple (`inline`, `IDs`, `classes/attrs/pseudo-classes`, `elements/pseudo-elements`) — most specific wins; ties broken by source order (last declared wins).

## Why it matters

Specificity is the single most common source of "why isn't my CSS applying?" frustration. For modern frontend work — especially with [[utility-first-css|utility-first]] systems where dozens of classes compose on one element — knowing how specificity is computed and how it interacts with class composition libraries (`clsx`, [[tailwind-class-composition|`tailwind-merge`]]) is required to debug effectively.

## The specificity tuple

For any selector, count:

1. **Inline styles** (`style="..."`) — the highest level.
2. **IDs** (`#nav`) — second level.
3. **Classes, attributes, pseudo-classes** (`.btn`, `[type="text"]`, `:hover`) — third level.
4. **Elements and pseudo-elements** (`div`, `::before`) — lowest level.

Compare tuple component-by-component, left to right. First larger number wins.

```
#nav .item             →  (0, 1, 1, 0)
.nav .menu .item       →  (0, 0, 3, 0)
                          ↑ #nav .item wins because 1 ID > 0 IDs
```

### `!important`

Trumps everything in its layer. Avoid; if you need it, you've probably got a deeper problem.

### Inline `style` vs `!important` in stylesheet

Inline `style` *loses* to a stylesheet rule with `!important`. (Yes, inline isn't supreme.)

## The cascade order (when specificity ties)

When specificity is identical, the **later-declared rule wins**. This is what `class="px-2 px-4"` relies on — both have identical specificity (one class each), so source order in the generated stylesheet decides which one applies. **Tailwind's class order in your markup is irrelevant**; the order in the *generated CSS* is what matters. This is why [[tailwind-class-composition|`tailwind-merge`]] exists — to dedupe conflicting Tailwind utilities at the markup level rather than rely on stylesheet order.

## Why utility-first changes the specificity story

In [[utility-first-css|utility-first CSS]]:

- **Every utility class has identical specificity** (one class each).
- **Conflicts resolve by source order** in the generated CSS.
- **Tailwind generates utilities in a fixed order** — `p-*` before `px-*` before `pl-*`, etc.
- **`class="px-2 px-4"` produces `px-4`** because `px-4` is later in the generated CSS.
- **`class="px-2 p-4"` produces `p-4`** for the same reason.

But you can't *count* on stylesheet order. Configuration changes, plugin order, custom utilities — all can shift things. [[tailwind-class-composition|`twMerge`]] enforces predictable last-wins behavior at the application layer, regardless of stylesheet order.
